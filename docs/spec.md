## 1. 目的と対象ユーザー

### 何のために
Typst で書かれた技術書リポジトリを、**Mac を開かずにスマホのブラウザだけで「編集 → 組版結果の確認（記事も本全体も）」まで完結**させる。同じ作業を LLM（Claude）にも任せられるようにする。**コミット・push・PR は studio の仕事にしない**（ユーザーまたは Claude が git / gh コマンドで行う）。

### 解く課題
| 現状 | typst-studio 導入後 |
|---|---|
| Mac で `typst compile` しないと見た目が分からない | 常時稼働の Linux サーバーがビルドし、ブラウザでプレビュー |
| 本全体の仕上がりは PDF を落として開かないと見られない | 本全体の PDF をアプリ内で表示。再ビルドしてもページ位置を保つ |
| 画像サイズは `width: 70%` を手で書き換えて再ビルド | プレビューの画像をタップしてスライダーで変更。ソースは自動で書き換わる |
| LLM に書かせても組版結果を LLM 自身が確認できない | MCP 経由でコンパイル診断・ページ画像を取得できる |

### 対象ユーザー
| ユーザー | 使い方 | 優先度 |
|---|---|---|
| リポジトリのオーナー（1 名） | スマホのブラウザ（tailnet 経由）。たまに PC。Git 操作は SSH か Claude に依頼 | 最優先 |
| LLM エージェント（Claude Code） | 同じサーバー上でプロジェクトのディレクトリを直接編集し、git / gh を実行。組版の確認は MCP | 高 |
| 他の執筆者 | **対象外**（マルチユーザー・同時編集はやらない） | — |

### 対象外
- **Git の操作 UI**（ブランチ作成・コミット・push・PR・マージ・差分表示）
- リアルタイム共同編集（CRDT）、アカウント管理、インターネット公開
- デスクトップ / モバイルネイティブアプリ
- Typst テンプレート自体のデザイン編集 UI

## 2. リポジトリの規約

### 2.1 方針
**リポジトリのルートに `typst-studio.toml` を 1 枚置けば対応リポジトリになる。** ディレクトリ形状は設定で宣言し、既存リポジトリを作り替えさせない。

### 2.2 参考リポジトリの現状（sample-book）

[確認済]
- ルートに `main.typ`（本全体）、`preview.typ`（記事単体プレビュー用。`sys.inputs` の `ARTICLE` と `CATEGORY` を受ける）、`template.typ`、`theme.typ`、`emo.typ`
- 記事は `articles/<slug>/article.typ`。**2 階層のものもある**（`articles/<slug>/<sub>/article.typ`）
- 記事ごとに `images/`、`figures/`（SVG）、メモ `.md`、データ `.yaml`
- `fonts/` に OFL フォント 7 ファイル・約 13MB を同梱。テンプレートはフォールバックとして `Noto Sans CJK JP` を名指ししている
- `sys.inputs` は `EBOOK` / `COLOR` / `GUIDE`（本全体）と `ARTICLE` / `CATEGORY`（記事単体）
- 作業ツリーは 221 ファイル・約 105MB、`.git` は約 339MB
- CI は typst **v0.14.2 固定**。`scripts/build-book.sh` で印刷版・電子版をビルドし、pdftk / pdfunite で表紙を結合
- `image(...)` 呼び出しは約 70 箇所。うち**パスが文字列リテラル直書きのものが約 6 割**、残りは変数や自作関数経由（テンプレート・テーマ内が中心）。grep による概算
- `chapter-title-page(title, image_path, height, voffset, category:)` は位置引数でサイズを取る

### 2.3 設定ファイル `typst-studio.toml`（案）

```toml
[project]
name = "sample-book"
typst = "0.14.2"            # CI と揃える。本全体のビルドはこの版の typst CLI を使う

[fonts]
paths = ["fonts"]           # --font-path に渡す。リポジトリ相対
system = true               # false で --ignore-system-fonts。移植性のため false を推奨（10.3）

[book]                      # 本全体
entry = "main.typ"
preview_profile = "print"   # 「本」タブで既定表示するプロファイル（[profiles.*] の名前）

[preview]                   # 記事単体プレビュー。無ければ book.entry をそのまま使う
entry = "preview.typ"
inputs = { ARTICLE = "{article_entry}", EBOOK = "true" }

[articles]
glob = "articles/**/article.typ"
image_dirs = ["images", "figures"]   # 記事ディレクトリ相対
upload_dir = "images"                # 画像アップロード先（記事ディレクトリ相対）

[[articles.override]]       # 記事ごとの追加 inputs（任意）
match = "articles/author-b/**"
inputs = { CATEGORY = "example" }

[profiles.print]
entry = "main.typ"
output = "main.pdf"

[profiles.ebook]
entry = "main.typ"
inputs = { EBOOK = "true" }
output = "ebook-body.pdf"

[profiles.guide]
entry = "main.typ"
inputs = { GUIDE = "true" }
output = "guide.pdf"

[[image_fn]]                # image() 以外で画像サイズを取る自作関数（Phase 3）
name = "chapter-title-page"
path_arg = 1                # 位置引数の番号（0 始まり）
size_args = { height = 2, voffset = 3 }
```

- **Git に関するキーは持たない。** studio はブランチを作らず、base ブランチも知らない（5 章）

### 2.4 適合に必要な変更
| リポジトリ | 必要な変更 |
|---|---|
| sample-book | `typst-studio.toml` を 1 ファイル追加するだけ。Phase 0 でファイル無変更のままコンパイルできた [確認済] |
| 新規の本 | `typst-studio init` 相当のひな型生成は Phase 3 以降 |

### 2.5 受け入れ条件
- `typst-studio.toml` が無いリポジトリを開くと、不足を説明するエラーを返す（黙って推測で動かない）
- 未知のキー（`[git]` を含む）・存在しないパス・`{article_entry}` 以外の未定義プレースホルダは、起動時に検証エラーになる
- `book.preview_profile` が `[profiles.*]` に無い名前なら検証エラーになる
- `articles.glob` で 2 階層の記事も列挙される
- リポジトリ外を指すパス（`..`、絶対パス、シンボリックリンク越え）は拒否する

## 3. アーキテクチャ

### 3.1 全体方式の比較（何を使い、何を自作するか）

| 案 | 概要 | メリット | デメリット | 実装コスト | 運用コスト | 評価 |
|---|---|---|---|---|---|---|
| **A. 自作シェル + tinymist preview** | サーバー側で tinymist がコンパイル。エディタ・ファイル API・PDF ビューア・MCP を自作 | 増分描画と相互ジャンプを流用できる。スマホは描画だけ。LLM 連携を自由に設計できる | tinymist のプレビューをリバースプロキシ越しに埋める検証が要る | 中（3〜5 週 [推測]） | 追加費用 0 円 | ◎ |
| B. 既存 OSS を採用（TOSS / Collabst） | セルフホスト型の共同編集基盤を入れる | 作る量が最少 | PostgreSQL + Docker 前提（TOSS）。ブラウザ側コンパイル。共同編集が主眼で、画像 UI・MCP は無い。AGPL。いずれも初期段階 | 低〜中（改造するなら高） | DB 常駐でメモリ増。追従保守 | △ |
| C. typst.app（公式）+ Git 同期 | 公式 Web アプリにリポジトリを連携 | 作らない。品質は最高 | サーバーの LLM から操作できない。Free は 200MB / 100 ファイル制限で本リポジトリ（221 ファイル）は収まらない。同期不調の報告あり | 0 | Pro 月額 $7.99（年 約 $96）。Git 同期に必要なプランは [未確認] | △ |

**推奨: A。** 要望の 3 本柱（サーバーでビルド / 本全体まで見られる / LLM から動かす）を同時に満たすのは A だけ。

補足: code-server（ブラウザ版 VS Code）+ tinymist 拡張は最小工数だが、スマホでの操作性が悪く画像 UI も作れないため候補から外した。

### 3.2 コンパイル場所の比較

| 観点 | サーバー側コンパイル（tinymist） | ブラウザ内 WASM コンパイル（typst.ts） |
|---|---|---|
| N100 の負荷 | 編集中のみ CPU を使う。1 プロセスに制限すれば許容 ○ | ほぼ 0 ◎ |
| スマホの負荷 | 描画用 WASM のみ（約 350KB）◎ | コンパイラ WASM 約 7.6MB を読み込み、端末でコンパイル △ |
| フォント配信 | 不要（サーバーが持つ）◎ | 同梱フォント 13MB + Noto CJK を端末へ配信 ✗ |
| 画像・素材 | 不要 ◎ | 作業ツリー約 105MB を仮想 FS として端末へ送る必要 ✗ |
| CI との一致 | 同じサーバーで typst 0.14.2 のビルドも回せる ◎ | typst.ts の追従版に依存 △ |
| LLM からの利用 | 同じコンパイル結果を MCP で返せる ◎ | ブラウザが開いていないと結果が無い ✗ |
| オフライン | 不可 △ | 可 ○ |

**推奨: サーバー側コンパイル。** WASM サイズの数値は typst.ts の旧版ドキュメントの値で、最新版は [未確認]。

### 3.3 プレビュー方式

#### 3.3.1 部品は 2 つ
| 部品 | 中身 | 増分 | ソースへのジャンプ | 入稿物との一致 |
|---|---|---|---|---|
| **V1. tinymist preview の埋め込み** | サーバーの tinymist が差分ベクタを WebSocket で配信し、ブラウザ側（typst.ts）が描く | あり | あり | △ フォーク版コンパイラ + 別レンダラ |
| **V2. PDF + pdf.js** | typst CLI 0.14.2 で PDF を作り、ブラウザの pdf.js で表示 | なし | なし | ◎ CI と同じコンパイラ（表紙結合だけ違う） |

#### 3.3.2 本全体プレビューの方式比較

| 観点 | (a) tinymist で本全体 | (b) すべて PDF + pdf.js | **(c) 併用: 記事 = tinymist、本全体 = PDF** |
|---|---|---|---|
| サーバーのメモリ | 常駐 約 1.0GB（実測 1,029MB）。上限 1.5GB が要る。本のビルド（約 1.0GB）と同時に動かせない ✗ | ビルド中だけ約 1.0GB、終われば 0 ◎ | 常駐 約 256MB + ビルド中だけ約 1.0GB。ピーク合計 約 1.3GB ○ |
| 更新の速さ | 105ms ◎ | 記事 1.0 秒 / 本全体 3.7 秒 △ | 記事 33ms ◎ / 本全体 3.7 秒 ○ |
| スマホの通信量 | 接続のたびに **44.3MB**（再接続でも再送）✗ | PDF 49.1MB。Range 取得で見ているページ分だけ [推測: 取得量は未計測] ○ | 記事 10.3MB / 本は見ているページ分 ○ |
| スマホの描画負荷 | 90 ページ分の SVG。`--partial-rendering` は experimental △ [未確認] | 表示中の前後数ページだけ描く ○ [未確認] | 同左 ○ |
| 入稿物との一致 | △ | ◎ | 本全体は ◎、記事は △ |
| ソースへのジャンプ・直接操作（4.7） | 本全体でも可 ◎ | 不可 ✗ | 記事で可、本全体は不可 ○ |
| 実装コスト | 低 | 中（ビルドキュー + ビューア） | 中〜高（V1 + V2。ただし V2 は本のビルド機能と共通） |
| 運用コスト | 0 円 | 0 円 | 0 円 |
| 評価 | △ | ○ | **◎** |

**推奨: (c)。**
- (a) は利用可能メモリ約 2.9GB・swap 満杯の現ホストで、常駐 1GB + ビルド 1GB が両立しない。スマホが再接続するたびに 44MB 流れるのも重い
- (b) は入力ごとの即時更新と、タップでソースへ飛ぶ操作（直接操作の土台）を失う
- (c) は「書いている最中は記事を即時に、仕上がりは本全体を入稿物と同じコンパイラで」と役割が分かれる。**本全体プレビューと検証ビルドは同じ機能になる**ので、作る量は見かけより少ない
- (a) は捨てない。tinymist の起動引数を変えるだけなので、メモリに余裕のあるホストではホスト側設定で有効化できるようにする（Phase 3）

#### 3.3.3 V1（tinymist preview）の埋め込み

[確認済: Phase 0]
- `--input` / `--font-path`（複数は `:` 区切り）/ `--root` / `--data-plane-host` / `--control-plane-host` が通る。静的ページ（1.6MB の HTML 1 枚）はデータプレーンと同じポートで配信される
- ページは **自分と同じオリジンのルート `/`** に WebSocket を張る（ホスト・ポートの埋め込みは無い）
- WebSocket の `Origin` は `http://127.0.0.1` / `http://localhost`（ポート不問）だけ通る。tailnet のホスト名・IP は切断
- コントロールプレーンは接続 1 本が前提。切ると tinymist が終了することがある（挙動は一定しない）
- コントロールプレーンのメッセージ: エディタ → プレビュー `changeCursorPosition` / `panelScrollTo` / `syncMemoryFiles` / `updateMemoryFiles` / `removeMemoryFiles`、プレビュー → エディタ `editorScrollTo` / `compileStatus` / `outline`

決めごと
| 項目 | 方式 |
|---|---|
| ページの配信 | studio が tinymist の HTML を `/preview/` で中継し、iframe で埋める |
| WebSocket | studio は**ルート `/` への WebSocket 接続を tinymist のデータプレーンへ中継**し、`Origin` を `http://127.0.0.1:<port>` に付け替える。studio 自身の WebSocket は `/api/ws` に置き、`/` を使わない |
| 制御接続 | studio サーバーが tinymist の寿命中ずっと 1 本保持する。ブラウザには直接つながせない |
| 停止 | 制御接続を切るのではなく、プロセス制限ドライバの停止（3.8.3）を呼ぶ |

[未確認] プロキシ越し・スマホ実機での動作は未検証。**Phase 1 の最初の作業で確かめる**（8 章）。駄目なら typst.ts のレンダラを自作フロントに組み込む。それも駄目なら記事も V2 にする（方式 (b)）。

#### 3.3.4 V2（PDF + pdf.js）

| 項目 | 方式 |
|---|---|
| ビルド | `typst compile`（0.14.2）を 1 回ずつ実行し、終わったらプロセスは消える。実測 3.7〜4.6 秒 / 最大 RSS 約 1GB |
| きっかけ | 「本」タブの「ビルド」ボタン。加えて、**「本」タブを表示している間だけ**保存の 5 秒後に自動ビルド（設定でオフにできる） |
| 対象 | **ディスクに保存済みの内容**（未保存のバッファは含まない） |
| 多重実行 | 同時に 1 本。ビルド中に保存が来たら、終わった後にもう 1 回だけ走る（途中のものは積まない） |
| 配信 | `$TYPST_STUDIO_HOME/builds/<project>/<profile>-<buildId>.pdf`。HTTP Range に対応。プロファイルごとに最新 2 世代だけ残す |
| 差し替え | 新しい PDF の該当ページを裏で描き終えてから入れ替える（白画面を挟まない） |
| ページ位置 | **ページ番号 + ページ内の縦位置（割合）+ 拡大率**を保つ。ページが減って無くなった場合は最終ページ |
| 失敗時 | 前回の PDF を表示したまま、診断（file:line:col）を出す |

- `typst watch` は常駐して約 1GB を持ち続ける見込みで、時間・メモリとも**未計測**。MVP では使わない。Phase 0.5 で測り、体感で遅ければ切り替えを再提案する
- pdf.js の配信サイズは 1〜2MB 程度 [推測]。スマホで 49MB の PDF（写真入り）を滑らかに描けるかは [未確認]。重ければ、サーバーが `typst compile --format png --pages` でページ画像を作って返す方式に退避する（MCP の `render_page` と共通）

### 3.4 バージョンの固定

[確認済]
| 対象 | 版 | 根拠 |
|---|---|---|
| typst CLI（本全体ビルド用） | v0.14.2 | 参考リポジトリの CI と同じ。Linux musl バイナリが配布されている |

- インストールは**配布バイナリを `$TYPST_STUDIO_DIST/bin/` に置く**（既定は `$TYPST_STUDIO_HOME`。10.3）（`scripts/setup.sh`。版数は変数で固定し、arch を判定して取得）。`cargo install` はしない（利用可能メモリ約 2.9GB・swap 満杯のため、Rust のビルドは危険）

### 3.6 フォント
**決定: studio 管理のフォントディレクトリ `$TYPST_STUDIO_DIST/fonts/` に置き、`--font-path` に足す**（sudo 不要。`scripts/setup.sh` が取得・照合する）。

| フォント | ウェイト | 状態 |
|---|---|---|
| Noto Sans CJK JP | Regular / Bold（32MB） | 配置済み [確認済]。PDF に埋め込まれるのはこの 2 つだけ |
| Noto Sans Mono CJK JP | Regular / Bold（32MB） | 配置済み [確認済]。追加後、本全体ビルドで「Mono が無い」警告が消え、IPAGothic が埋め込まれなくなった |

- 残る警告は可変フォント（Noto Emoji）の 1 件だけ（描画に支障なし）
- `--ignore-system-fonts` でビルドできることを確認できたら、`fonts.system = false` を既定にする（移設しても出力が変わらない。**コンテナ化の前提**: イメージにシステムフォントを入れない）
- CI は apt の `fonts-noto-cjk` を使う。フォントファイルの版が CI と同一かは [未確認]

### 3.7 プロジェクト（作業ディレクトリ）

**決定: プロジェクトごとに普通のディレクトリ `$TYPST_STUDIO_HOME/projects/<name>/` を置く（通常の `git clone`）。studio は worktree もブランチも管理しない。**

| 項目 | 内容 |
|---|---|
| 作り方 | `scripts/add-project.sh <name> <git-url>` が通常の clone を作る。手で clone して置いてもよい |
| studio が見るもの | そのディレクトリに**今チェックアウトされている内容**。どのブランチかは問わない |
| ブランチの切替・コミット・push・PR | ユーザーまたは Claude が、そのディレクトリで git / gh を実行する（5 章） |
| 並行作業 | 別ブランチを同時に開きたいときは、別名でもう 1 つ clone する（`projects/<name>-2/`）。1 つ約 445MB |
| 数の上限 | 設けない（空き 32GB） |
| 人間用の `~/workspace/<name>` | 触らない。別物として扱う |

- 外部でブランチが切り替わると、多数のファイルが一度に変わる。studio はファイル監視で検知し、一覧と開いているファイルを読み直す（6.4）
- studio はプロジェクトのディレクトリを**削除しない**。削除は人が行う
- 現状: `projects/sample-book/`（main）を配置済み [確認済]

### 3.8 プロセス数とメモリ上限（プロセス制限の抽象化）

#### 何のために
重いプロセス（tinymist / typst）が暴れても、studio 本体と同じホストの他サービスを巻き込まない。**現ホスト（systemd）と移設先（コンテナ、systemd 無し）の両方で同じコードが動く**ようにする。

#### 3.8.1 プロセスと上限値（方式に依らない）

[確認済] N100: 利用可能メモリ 約 2.9GB、swap 4GB は満杯。

| プロセス | 数 | メモリ上限 | swap | CPU | 実測 RSS | 備考 |
|---|---|---|---|---|---|---|
| studio サーバー（Node 24） | 1（常駐） | 300M | — | — | 未計測 | API・静的配信・WebSocket 中継・MCP |
| tinymist preview（記事） | **最大 1** | 600M | 0 | 200% / nice 10 | 256MB | 閲覧者 0 が 10 分続いたら停止 |
| typst compile（本全体 PDF・`render_page`） | **最大 1**（キュー） | 1500M | 0 | — | 約 1GB | タイムアウト 5 分。終わればメモリは 0 |

- 上限の合計 2.4GB、実測の合計 約 1.4GB。**重いプロセスは種類ごとに 1 本まで**。記事プレビューと本のビルドは同時に動いてよい
- 上限値はホスト側設定（10.3）から読む。上限の 8 割を超えたビルドは操作ログに残し、UI に注意を出す
- 上限で止まった場合は UI に「メモリ上限で停止」と表示し、自動再起動は 1 回まで

#### 3.8.2 コンテナ内での上限の掛け方（比較）

[確認済] コンテナ内に systemd は無く、`systemd-run --user --scope` は使えない。
[確認済: N100 で計測] typst（musl 静的）は仮想メモリのピーク 1,127MB が RSS 994MB に近く、`prlimit --as` が素直に効く（1200M で成功、900M で exit 134）。tinymist（glibc・10 スレッド）は仮想 843MB に対し RSS 212MB で約 4 倍の開きがあり、アドレス空間の上限では RSS を絞れない。

| 案 | 内容 | メリット | デメリット | 実装コスト | 評価 |
|---|---|---|---|---|---|
| P1. コンテナ全体の上限だけ | compose の `mem_limit` / `memswap_limit` のみ | 実装 0。ホストは必ず守られる | 上限到達時にどのプロセスが殺されるかはカーネル任せ。Node が落ちうる | 0 | △ |
| **P2. 全体の上限 + アプリ内の見張り** | P1 に加え、studio が子プロセスの RSS を 250ms 間隔で見て超過時に SIGKILL。typst には `prlimit --as` も掛ける。子の `oom_score_adj` を上げる | 追加の権限・コンテナ不要。**同じドライバがホストでも動くので N100 でテストできる** | 見張りは厳密ではない（ポーリング間に最大 70MB 程度超えうる [推測]）。厳密な保証は全体の上限が担う | 低（2〜3 日 [推測]） | **◎** |
| P3. cgroup v2 の委譲 | コンテナ内で子 cgroup を作り `memory.max` を書く | systemd scope と同じ厳密さ | 非特権コンテナでは `/sys/fs/cgroup` が読み取り専用。`privileged` 相当が要る [確認済] | 中 | ✗ |
| P4. 子プロセスを別コンテナにする | tinymist 用・typst 用のランナーコンテナに個別の `mem_limit` | カーネルによる厳密な種類別上限 | 起動・停止・出力中継のランナーを自作。コンテナ 3 つ | 中〜高（1 週 [推測]） | ○ |
| P5. `prlimit` だけ | `RLIMIT_AS` | 実装が最少 | tinymist に効かない | 低 | △（P2 の部品） |

**推奨: P2。** 守るべきは「ホストの他サービス」と「Node が落ちないこと」。前者は全体の上限で厳密に、後者は見張りと `oom_score_adj` で実用上足りる。Node が巻き込まれる事象が出たら、同じ抽象（3.8.3）の裏で P4 に差し替える。

- コンテナ全体の上限 = 300M + 600M + 1500M + 余裕 200M = **2600M**（`mem_limit` と `memswap_limit` を同値にして swap を使わせない [確認済]）
- [未確認] コンテナ内で `oom_score_adj` の書き込みが通ること、全体の上限到達時に殺されるのが 1 プロセスだけであること。移設時検証（8 章 M-V3）で確かめる

#### 3.8.3 抽象化: プロセス制限ドライバ

studio のコードは `systemd-run` を直接呼ばない。次のインターフェース越しに重いプロセスを起動する。

| 操作 | 内容 |
|---|---|
| 起動 | コマンド・作業ディレクトリ・環境変数と、上限（メモリ / swap / CPU / nice / タイムアウト）を渡す |
| 停止 | プロセス群ごと止める |
| 終了理由 | `ok` / `error` / `limit`（上限で停止）/ `timeout` / `stopped` を区別して返す |
| 空きメモリ | ビルド開始前の判定に使う値を返す |
| 能力の申告 | 上限が「厳密」か「見張り」か「無し」か。起動ログと UI の設定画面に出す |

| ドライバ | 使う場面 | メモリ上限 | swap / CPU | 空きメモリの出どころ | `limit` の判定 |
|---|---|---|---|---|---|
| `systemd-scope` | 現ホスト（D1） | scope の `MemoryMax`（厳密）[確認済] | `MemorySwapMax=0` / `CPUQuota` / `Nice` | `/proc/meminfo` の `MemAvailable` | scope の結果が `oom-kill` |
| `watchdog` | コンテナ（D2）、systemd の無いホスト | RSS の見張り + typst のみ `prlimit --as` | コンテナ全体の設定に委ねる。nice は付ける | cgroup の `memory.max − memory.current` と `MemAvailable` の小さい方 [推測] | 見張りが止めた / exit 134 / SIGKILL + `memory.events` の `oom_kill` 増加 [推測] |
| `none` | 開発・テスト | なし | なし | `MemAvailable` | 判定しない。起動時に警告 |

- 選び方: `limits.driver = "auto"`（既定）。`systemd-run --user --scope` が使えれば `systemd-scope`、使えなければ `watchdog`
- **ビルド開始前の確認**: 空きメモリが `build.memory_max` + 300MB に満たなければ始めず、「メモリ不足」と「プレビューを止めてビルド」ボタンを出す（両ドライバ共通）
- インターフェースはローカルの PID を前提にしない（将来 P4 のランナーを 1 ドライバとして足せるように）

#### 3.8.4 受け入れ条件
- studio のコードで `systemd-run` を呼ぶのは `systemd-scope` ドライバの 1 ファイルだけ（grep で検証）
- `limits.driver = "watchdog"` を N100 上で指定し、`build.memory_max = "300M"` で本全体をビルドすると、1 秒程度で止まり終了理由が `limit` になる。studio サーバーは動き続ける
- 同じ条件を `systemd-scope` で行っても、UI の表示（「メモリ上限で停止」）が同じ
- `watchdog` で typst に 900M 相当の上限を与えると `limit` として報告される（exit 134 を `error` と誤分類しない）
- 記事プレビューと本のビルドが、どちらのドライバでも同時に 1 本ずつまで
- 起動ログに、選ばれたドライバと能力（厳密 / 見張り / 無し）が 1 行出る

### 3.9 構成スタック（案）
| 層 | 採用 | 理由 |
|---|---|---|
| サーバー | Node 24 + TypeScript + Fastify | 既存ランタイム。WebSocket 中継と MCP SDK が揃う |
| フロント | Vite + React + CodeMirror 6 + pdf.js（pdfjs-dist） | CodeMirror 6 はモバイルの入力に強い。pdf.js は本全体の PDF 表示 |
| 状態保存 | ファイル（JSON）のみ。**DB は使わない** | postgres を巻き込まない |
| 外部サービス | **追加なし**（Tailscale は既存。GitHub には studio からは接続しない。移設先の Coolify はセルフホスト） | 追加の運用費 0 円 |

### 4.4 画像サイズ指定 UI

目的: `width` と `alt` を、ソースを開かずに直せるようにする。

方式
1. サーバーが `.typ` を走査し、`image(` 呼び出しを抽出する（文字列・コメント・括弧の入れ子を追うスキャナ）
2. **第 1 引数が文字列リテラルのものだけ編集可能**にする。変数・式のものは一覧に「編集不可」として出す
3. UI: サムネイル、`width`（% スライダー / mm 数値入力）、`height`、`alt` テキスト。入口は 2 つ: 画像タブの一覧 / **プレビューの画像をタップ（4.7）**
4. 書き換えは**その呼び出しの引数範囲だけ**を文字列置換する。他の行・整形には触らない
5. 書き換え後にプレビューが更新され、失敗したら 1 操作で元に戻せる

| 解析方式 | メリット | デメリット | 評価 |
|---|---|---|---|
| **S1. TypeScript の自作スキャナ（リテラル直書きのみ対象）** | ビルド不要。すぐ作れる | 複雑な式は扱えない（扱わないと割り切る） | ◎ MVP |
| S2. `typst-syntax`（Rust）で AST を取り、JSON で返す小さな CLI | 正確 | このサーバーでの Rust ビルドは負荷が厳しい。別環境でビルドして配る必要 | ○ 誤解析が出たら移行 |
| S3. tinymist の LSP に問い合わせる | 追加実装が少ない可能性 | 必要な情報が取れるか [未確認] | △ |

**推奨: S1。**

受け入れ条件
- 参考リポジトリで確認した形（`image("p")` / `image("p", width: 100%)` / `image("p", width: 70%, alt: "...")` / `image("p", width: 32mm)` / `image("p", height: 8em)`）を正しく抽出・書き換えできる
- `width` が無い呼び出しに追加でき、既存の `width` は値だけ差し替わる
- 書き換え前後の差分が、対象の呼び出しの引数範囲に限られる（テストで検証）
- 文字列内・コメント内の `image(` を拾わない
- `image(path, ...)` のような非リテラル呼び出しは変更しない
- `[[image_fn]]` で宣言した自作関数の位置引数（章扉の高さなど）は Phase 3

### 4.5 画像アップロード
- 送り先: 編集中の記事の `articles.upload_dir`
- 受け付け: png / jpeg / webp / svg。**1 ファイル 10MB まで**（仮）
- ファイル名: 小文字英数とハイフンに正規化。衝突時は連番
- アップロード後、カーソル位置に `#image("images/<name>", width: 100%)` を挿入するボタンを出す
- サーバー側のリサイズ・変換は MVP 対象外（N100 の負荷を避ける）
- 受け入れ条件: リポジトリ外へのパスを指定できない / 拡張子と中身（マジックナンバー）が一致しないものは拒否

### 4.6 本全体のプレビュー（= 検証ビルド）

目的: 入稿物と同じコンパイラで組んだ本全体を、ダウンロードせずにその場で見る。

- 「本」タブでプロファイル（print / ebook / guide）を選び、typst CLI 0.14.2 でビルドして pdf.js で表示する。方式は 3.3.4
- 同じ PDF をダウンロードできる
- ビルド時刻・所要時間・警告件数を出す。**ソースより古い PDF を表示しているときは「未反映の変更あり」と出す**
- **表紙との結合はしない。** pdftk / pdfunite がサーバーに無く、apt には sudo が要る。結合済み PDF は CI の成果物を使う

受け入れ条件
- 記事を 1 行直して保存 → 「本」タブで、手を触れずに 15 秒以内に新しい PDF に差し替わる（自動ビルド有効時）
- 差し替えの前後で、表示中のページ番号と拡大率が変わらない。差し替え中に白画面が出ない
- ページ数が減って表示中のページが無くなった場合、最終ページを表示する
- コンパイルエラー時は前回の PDF を表示したまま、file / line / column / message を出す
- ビルドが同時に 2 本走らない。連続保存しても、待ちは最大 1 本
- PDF の取得が HTTP Range（206）で行われる

### 4.7 プレビュー上での直接操作

目的: プレビューで気になった箇所を、ソースを探さずにその場で直す。

#### 仕組み
1. 記事プレビュー（tinymist）をタップすると、tinymist が `editorScrollTo`（ファイル・開始位置・終了位置）を制御接続へ送る [確認済: メッセージの存在。**画像のタップで届くかは未確認**]
2. studio サーバーがそれを受け、4.4 のスキャナが出した `image(` 呼び出しの範囲と照合する
3. 位置が `image(` 呼び出しの中 → **画像サイズのシート**を下から出す。それ以外 → 「ソースへ」チップを出す（スマホでは勝手にタブを切り替えない。スクロール中の誤タップ対策）
4. シートのスライダーを動かすと、メモリファイル更新で**プレビューが約 40ms で追従**する。「適用」でソースへ書き込み、「取り消し」で元に戻す

#### 段階
| # | 操作 | 方式 | 不確かな点 | 段階 |
|---|---|---|---|---|
| 1 | タップ → ソースへ飛ぶ | `editorScrollTo` | プロキシ越しで動くか [未確認] | **Phase 1（MVP）** |
| 2 | 画像をタップ → サイズ変更シート（スライダー・数値・alt） | `editorScrollTo` + 4.4 スキャナ | 画像のタップで位置が届くか [未確認] | **Phase 2** |
| 3 | 画像の縁をドラッグして幅を変える | iframe 内に自前のつまみを重ねる | typst.ts が作る DOM から画像の矩形を取れるか [未確認]。tinymist の版上げで壊れやすい | Phase 3（検証が通れば） |
| 4 | 本全体（PDF）のタップ → 該当記事を開く | PDF のしおり（`/Outlines` あり [確認済]）からページ → 見出し → 記事を引く | 見出しと記事の対応付け [推測] | Phase 3 |
| 5 | 本全体（PDF）上での画像サイズ変更 | — | PDF にソース位置を持たせる手段が見つからない [未確認]（下記） | やらない |

- 2 が不成立の場合の退避: タップで届いた位置に**最も近い `image(` 呼び出し**を候補として出す。それも当たらなければ、画像タブの一覧（記事内の出現順）から選ぶ
- 3 を待たなくても、2 のスライダーが即時追従するので「動かしながら決める」体験は得られる。**ドラッグは後回しでよい**

#### PDF 側でできない理由
- `typst compile` / `typst watch` のヘルプに、ソース位置を出力するフラグは無い [確認済]
- 生成した PDF の生バイトに `.typ` のパスは無い [確認済]。圧縮ストリーム内までは見ておらず、PDF から位置を引ける手段が**存在しないことの確認は取れていない** [未確認]
- 同じソースを tinymist に読ませて「ページ + 座標 → ソース」を引く手は理屈上あるが、本全体の tinymist（約 1GB）を起こす必要があり、(c) を選んだ理由と矛盾する

#### 受け入れ条件
- （段階 1）記事プレビューの本文をタップ → 「ソースへ」チップ → エディタが該当ファイルの該当行を表示する（別ファイルの場合はそのファイルを開く）
- （段階 2）リテラル直書きの `image()` で描かれた画像をタップ → シートにその呼び出しの現在の `width` が出る
- （段階 2）スライダー操作中、ソースのファイルは書き換わらない。「適用」で初めて書き換わり、差分は対象の呼び出しの引数範囲に限られる
- （段階 2）非リテラルの `image()`・テンプレート内の画像をタップした場合は、「編集不可」と該当ソースへのリンクだけを出す

## 5. Git との関係

### 何のために
Git の操作を studio から切り離し、**作るものを減らす**。コミット・push・PR は、ユーザーまたは Claude が慣れたコマンドで行う。

### 5.1 役割分担
| すること | 誰が | どこで |
|---|---|---|
| clone | ユーザー / Claude（`scripts/add-project.sh`） | `$TYPST_STUDIO_HOME/projects/<name>/` |
| ブランチ作成・切替、pull | ユーザー / Claude | 同じディレクトリで git |
| 編集・保存 | ユーザー（studio の UI）/ Claude（ファイルを直接編集） | 同上 |
| プレビュー・本全体の PDF | **studio** | — |
| コミット・push・PR・CI の確認 | ユーザー / Claude | git / gh |
| マージ | ユーザー | GitHub |

典型的な流れ: スマホで studio を開いて直す → プレビューと本全体を確認 → SSH の Claude Code に「ブランチを切って PR にして」と頼む。

### 5.2 studio が Git についてすること
| 項目 | 内容 |
|---|---|
| 表示 | 現在のブランチ名（detached なら短縮ハッシュ）、未コミット件数、未 push 件数 |
| 取得方法 | `git --no-optional-locks status --porcelain=v2 --branch` の読み取りだけ。ファイル監視で `.git/HEAD` と作業ツリーの変化を見て更新 |
| 書き込み | **一切しない**（add / commit / checkout / fetch / pull / push / stash / worktree を実行しない） |
| 認証情報 | **持たない**。GitHub へ接続しない。gh のトークンを読まない |

ブランチ名・件数の表示を入れる理由: コストが小さく（コマンド 1 本）、「main のまま編集していた」という取り違えを防げる。

### 5.3 外部の Git 操作への追従
| 起きること | studio の動作 |
|---|---|
| ブランチ切替・pull でファイルが一斉に変わる | 記事一覧を作り直し、開いているファイルを読み直す。tinymist はディスクの変更を拾って再コンパイルする |
| 開いている記事がそのブランチに無い | 「このブランチには存在しません」と出し、記事一覧へ戻す |
| ブラウザ側に未保存の編集がある | 6.4 の競合手順（勝手に上書きしない） |
| `typst-studio.toml` が変わった | 設定を読み直す。検証エラーならその内容を出す |
| 衝突マーカーがファイルに入った | そのまま表示する（コンパイルエラーになる）。解決は Git 側で行う |

### 5.4 CI との関係
| 項目 | studio | CI（GitHub Actions） |
|---|---|---|
| 役割 | 執筆中の速い確認と、本全体の事前確認 | 入稿物の正 |
| Typst | 記事: tinymist 0.14 系 / 本全体: typst 0.14.2 | typst 0.14.2 |
| 表紙結合 | しない | する |
| フォント | 同梱 + studio 管理の Noto Sans CJK JP / Noto Sans Mono CJK JP | 同梱 + apt の fonts-noto-cjk |

- `typst-studio.toml` の `typst` と CI の版のずれ検出は Phase 3。それまでは README に注意書き

### 5.5 受け入れ条件
- studio のコードが実行する git コマンドは、読み取り専用の許可リスト（`status` / `rev-parse`）に限られる。それ以外を呼ぶとテストが落ちる
- 外部で `git switch` した後、5 秒以内に UI のブランチ名が変わる
- 外部で 1 ファイルを書き換えて未コミットにすると、件数が 1 増える
- studio の実行環境に `GH_TOKEN` が無く、gh が未認証（コンテナ内に gh が存在しない）でも、全機能が動く

## 6. LLM 連携

### 何のために
Claude が自分で書いた結果の**組版を自分で確かめられる**ようにする。編集と Git は Claude Code の標準機能（ファイル編集・シェル）で足りるので、studio は「確かめる」部分だけを提供する。

### 6.1 方式
| 案 | 内容 | 評価 |
|---|---|---|
| **L1. studio サーバーが MCP（Streamable HTTP）を `127.0.0.1` で公開** | UI と同じビルドキュー・同じメモリ上限を通る。移設先でも同じ URL（compose が `127.0.0.1` に公開） | ◎ |
| L2. stdio の MCP サーバーを別プロセスで用意 | 登録が単純 | ○ ビルドキューを共有できず、メモリ上限を二重に持つ |
| L3. MCP を作らず、Claude に `typst compile` を直接叩かせる | 実装 0 | △ UI のビルドと同時に走ると合計 2GB を超えうる。フォント・inputs の指定を毎回間違えうる |

**推奨: L1。**

登録例: `claude mcp add --transport http typst-studio http://127.0.0.1:8796/mcp`（ポートはホスト側設定）

### 6.2 ツール一覧
| ツール | 内容 | 書き込み | 段階 |
|---|---|---|---|
| `list_projects` | プロジェクト名、パス、現在のブランチ、未コミット件数 | なし | 2 |
| `list_articles` | 記事の一覧（パス、画像数） | なし | 2 |
| `compile` | プロファイルまたは記事を指定。診断（file:line:col）を構造化して返す。ビルドキューを通る | なし | 2 |
| `render_page` | 指定ページを PNG で返す（既定 100ppi、上限 1 回 4 ページ） | なし | 2 |
| `list_images` | `image()` 呼び出しの一覧（位置、width、alt、編集可否） | なし | 2 |
| `set_image_attrs` | width / height / alt を書き換える。対象の現在の文字列を添え、違っていたら拒否 | **あり** | 2 |

外したもの
| 旧ツール | 理由 |
|---|---|
| `read_file` / `write_file` | Claude Code は同じサーバーでディレクトリを直接読み書きできる。変更はファイル監視で UI に届く |
| `create_workspace` | worktree を管理しない（3.7） |
| `git_status` / `git_diff` / `git_commit` / `git_push` / `create_pr` | Claude が git / gh を直接実行する（5 章） |

- 既存の Typst 向け MCP（ドキュメント検索・構文チェック系）は存在するが、リポジトリを開いてコンパイル診断を返すものは見つからなかった。この部分は自作する

### 6.3 権限の線引き
- MCP は Git を一切実行しない。コミット・push をどこまで Claude に許すかは、**Claude Code 側の権限設定とユーザーの指示**で決まる（studio の関知外）
- MCP が書き込むのは `set_image_attrs` だけで、対象は `articles.glob` 配下の `.typ` に限る
- すべての MCP 呼び出しを操作ログ（JSON Lines）に残す

### 6.4 同時編集の競合
人と Claude が**同じディレクトリ**を触る前提で設計する。

| 状況 | 動作 |
|---|---|
| 外部（Claude・ターミナル・git）がファイルを変更、ブラウザ側は未編集 | 自動で読み直す |
| 外部が変更、ブラウザ側に未保存の編集あり | 「外部で変更されました」と差分を出し、どちらを残すか選ばせる。自動保存は止める |
| ブラウザの保存時、開いたときの `rev`（内容ハッシュ）とディスクが違う | 保存を拒否し、上と同じ選択を出す |
| `set_image_attrs` の対象文字列が現状と違う | 拒否し、最新の一覧を返す |

- ファイル監視は `.git/` と `node_modules/` を除外する（`.git/HEAD` だけは見る）
- CRDT は導入しない
- Claude に長い作業を任せる間、同じ記事を UI で編集しないのが安全。別ブランチで並行させたいときは別名で clone する（3.7）

### 6.5 受け入れ条件
- `compile` がエラー時に file / line / column / message を返す
- `render_page` が返す PNG に日本語が正しく出る（豆腐にならない）
- UI のビルドと MCP の `compile` を同時に要求しても、typst のプロセスは同時に 1 本
- 古い `rev` でのブラウザ保存が拒否される
- Claude がファイルを直接書き換えると、5 秒以内に UI のエディタとプレビューに反映される（ブラウザ側が未編集の場合）
- MCP に Git を実行するツールが無い

## 7. ホスティングと認証

### 7.1 構成

| 項目 | 現ホスト（N100、D1） | 移設先（自宅サーバー + Coolify、D2） |
|---|---|---|
| 動かし方 | `systemctl --user` の unit（linger 有効を確認済） | Coolify が Docker Compose でデプロイするコンテナ 1 つ（10.8） |
| studio のバインド | **`127.0.0.1` のみ。違反なら起動しない** | コンテナ内は `0.0.0.0:8796`（ポート公開の仕組み上必須）。**ホスト側は compose の `ports` で `127.0.0.1:8796` にだけ公開**。コンテナ実行時だけループバック検査を外す（10.3） |
| ポート | 既定 `8796`。tinymist のデータ / コントロールプレーンも `127.0.0.1` | 同じ。tinymist はコンテナ内の `127.0.0.1`（外へ公開しない） |
| 外部到達 | `tailscale serve`（tailnet 限定の HTTPS）→ `http://127.0.0.1:8796` | **同じ**（ホストの `tailscale serve` → `127.0.0.1:8796`）。**Coolify のドメインは割り当てない = Coolify のプロキシ（Traefik）を通さない**（7.5） |
| MCP | `http://127.0.0.1:8796/mcp` | 同じ URL（ホストの Claude Code から。10.9） |
| tinymist | studio が必要時に起動・停止。常駐させない | 同じ（同一コンテナ内の子プロセス） |

- 「LAN から」の利用も **tailnet 経由に統一**する。LAN の IP に公開する構成は取らない
- 現ホストで `tailscale serve` の設定変更が sudo 無しで通るかは [未確認]。通らなければ、ユーザーに次を 1 回実行してもらう
  `! sudo tailscale serve --bg --https=8445 http://127.0.0.1:8796`

### 7.2 認証

| 案 | 内容 | 評価 |
|---|---|---|
| **N1. tailnet 限定 + Tailscale の識別ヘッダで許可リスト** | `tailscale serve` が付ける `Tailscale-User-Login` を見て、許可ユーザー（`auth.allow_users`）以外を拒否 | ◎ |
| N2. tailnet 限定のみ | 追加実装なし | ○ tailnet を共有していなければ十分 |
| N3. 独自のログイン | パスワード管理が増える | △ |

**推奨: N1（現ホスト・移設先とも）。**

> **v0.5 追記（2026-11-23）: 認証は前段の Cloudflare Access に任せる方針（ユーザー決定）。** studio の既定は `auth.mode = "external"`（ユーザーの照合はせず、Origin 検査とパスの検査だけ行う）。許可リスト（N1）は `auth.mode = "tailscale"` として残す。Cloudflare Access の JWT（`Cf-Access-Jwt-Assertion`）の検証と、公開経路（Cloudflare Tunnel 等）の設計は未決（9.2 #24）

[確認済] 識別ヘッダは `tailscale serve` が tailnet からの通信に付ける。Funnel とタグ付き端末からの通信には付かない。クライアントが同名ヘッダを送ってきた場合、serve が取り除く。バックエンドは localhost だけで待ち受けるのが前提。

**判定規則（v0.4 で変更）**

| リクエスト | 扱い |
|---|---|
| `Tailscale-User-Login` あり | 許可リストと照合。外れたら 403 |
| ヘッダなし + パスが `/mcp` または `/healthz` | 許可（同一ホストからの直接アクセス） |
| ヘッダなし + それ以外（UI・ファイル API・WebSocket） | **拒否（401）**。v0.3 は「127.0.0.1 からなら許可」だった |

変更の理由: コンテナでは接続元 IP が常に Docker のゲートウェイになり、「127.0.0.1 からかどうか」で区別できない。誤って Coolify のドメインを割り当てても、ヘッダ無しで UI まで素通りしない。開発時に curl で UI の API を叩くときは `auth.mode = "none"` を使う。

- 同一ホストの他プロセスからは守れない点は受容する（単一ユーザー機）。**移設先では「同じサーバーの他の Coolify アプリ」も含まれうる**ため、studio のスタックを Coolify の共有ネットワークに繋がない（7.5）

### 7.3 セキュリティ上の決めごと
- ファイル API はすべてプロジェクトのルート配下に正規化し、外へ出るパスを拒否。`.git/` 配下への書き込みも拒否
- 状態を変える API は `Origin` を検査する（CSRF 対策。許可値は `public_url` から導出）
- **studio は GitHub の認証情報を持たない。** git の書き込み・gh を実行しない（5.2）。コンテナにもトークン・SSH 鍵・gh を入れない（10.5）
- tinymist のデータプレーン・コントロールプレーンは `127.0.0.1` のみ。ブラウザからは studio の中継だけを通る
- Typst パッケージ（`@preview/...`）のダウンロードは外部通信になる。参考リポジトリは `@preview/tiaoma:0.3.0` を使っており、初回コンパイル時に packages.typst.org から取得される [確認済]
- （移設先）compose の `ports` はすべて `127.0.0.1:` 始まり。Docker が公開したポートは ufw を素通りするため、ファイアウォール頼みにしない [確認済]
- （移設先）Docker Engine 28.0.0 未満では、`127.0.0.1` に公開したポートへ同一 L2 セグメントのホストから届きうる [確認済]。**28 以上を要件にする**（10.7）
- （移設先）コンテナは非 root（ホストの作業ユーザーと同じ UID）で動かし、`cap_drop: ALL` / `no-new-privileges` / Docker ソケットを渡さない

### 7.4 運用コスト

| 項目 | 現ホスト | 移設先 |
|---|---|---|
| 追加の外部サービス | なし（0 円） | なし（0 円）。Coolify はセルフホスト |
| GitHub Actions | 既存どおり | イメージのビルド確認を足す場合は 8 章 M-3 |
| ディスク | 約 1GB | データ 約 0.8GB + イメージ 約 500MB [推測]。旧イメージは定期的に掃除する |
| メモリ | 常駐: Node 約 150MB [推測]。編集中 + 256MB。ビルド中 + 約 1.0GB | 同じ + Coolify 自体（最低要件 2 コア / 2GB / 10GB [確認済]） |
| 手間 | unit の更新は手動 | デプロイは Coolify のボタン 1 回。tailnet 限定のダッシュボードには Webhook が届かないため、自動デプロイは使わない [確認済] |

### 7.5 移設先での tailnet 限定公開（方式比較）

| 案 | 内容 | 可否 | 識別ヘッダ（N1） | 手間 | 評価 |
|---|---|---|---|---|---|
| **T1. ホストの `tailscale serve` → `127.0.0.1:8796`** | サーバー自体を tailnet に参加させ、compose でポートを `127.0.0.1` にだけ公開。Coolify のドメインは付けない | 可 [確認済: 公開事例あり。compose の `ports` は Coolify のプロキシを経由しない] | **付く** | root でコマンド 1 回（または `tailscale set --operator`） | **◎** |
| T2. Compose に Tailscale のサイドカー | `tailscale/tailscale` コンテナを同じスタックに入れ、`TS_SERVE_CONFIG` で serve を設定 | 可 [確認済] | **付く** | 認証キーを Coolify のシークレットに登録、状態用ボリューム。tailnet 上は別ノードになり、**サーバーを替えても URL が変わらない** | ○ |
| T3. Coolify のプロキシ（Traefik）を tailnet の IP にだけ公開 | プロキシの compose のポートを書き換える | [未確認] 公式手順なし。起動順で失敗する報告あり | **付かない** → N2 に後退 | サーバー上の全アプリに影響 | ✗ |
| T4. Coolify の機能でアクセス制限 | Traefik の IP 許可リストなど | [未確認] 公式手順なし | **付かない** | 中 | ✗ |

**推奨: T1。** 現ホストと経路が同じなので、認証・Origin 検査・MCP の URL がそのまま使え、コードの分岐が増えない。「サーバーを替えても URL を変えたくない」「ホストで root の作業をしたくない」なら T2 に切り替える（studio 側の変更は不要）。

T1 の決めごと
- Coolify でこのサービスに**ドメインを割り当てない**。「Connect to predefined network」を有効にしない（スタック専用ネットワークのまま）[確認済]
- T2 を選ぶ場合の追加シークレットは `TS_AUTHKEY` の 1 つ。Coolify で「ロック」して値を見えなくする [確認済]

### 7.6 受け入れ条件（移設先）
- ホスト上で `ss -ltnp` を見て、8796 が `127.0.0.1` にだけ出ている
- LAN の別端末から `http://<LAN の IP>:8796/` に届かない
- スマホ（tailnet）から `public_url` を開くと UI が出る。許可リスト外のログイン名は 403
- ホスト上の `curl http://127.0.0.1:8796/api/...`（ヘッダなし）が 401、`/healthz` が 200、`/mcp` が MCP の応答を返す
- Coolify の画面でこのサービスのドメイン欄が空。Traefik にこのサービス向けのルートが無い

## 10. 移植性と別サーバーへの移設

### 何のために
N100 機はメモリが厳しい（利用可能 約 2.9GB・swap 満杯）。**自宅サーバーへ移し、Coolify でデプロイする**（D10）。移設を「ホスト側の準備 1 回 + Coolify の設定 1 回 + 未 push 分の push」で終わる作業にするため、ホスト固有の値をコードとリポジトリ設定から追い出しておく。公開範囲は移設後も tailnet 限定。

- N100 は引き続き D1（systemd --user）で動かす。**同じコードが D1 と D2 の両方で動くこと**がこの章の要件
- Coolify の導入と `tailscale serve` の設定は root が要るため **ユーザーが行う**。studio 自体は root を要求しない

### 10.1 移設で変わるもの／変わらないもの

| 項目 | 現環境（N100） | 移設先（Coolify） | 対処 |
|---|---|---|---|
| studio のコード・UI・MCP ツール | — | 変わらない | — |
| リポジトリ側 `typst-studio.toml` | リポジトリに同梱 | 変わらない | ホスト固有の値を入れない（10.3） |
| typst / tinymist の版 | 0.14.2 / 0.14.18 | 変わらない | `setup.sh` の変数。イメージのビルド引数で同じ値を渡す |
| 動かし方 | user unit | Coolify（Docker Compose） | 10.8 |
| バイナリ・フォントの置き場 | `$TYPST_STUDIO_HOME/bin` `fonts` | **イメージ内 `/opt/typst-studio/`** | `TYPST_STUDIO_DIST` で分離（10.3） |
| データ置き場 | `~/.local/share/typst-studio/` | **ホストのディレクトリを bind mount** | ホストとコンテナで同じ絶対パスにする（10.9） |
| プロセス制限 | `systemd-scope` ドライバ | `watchdog` ドライバ + コンテナ全体の上限 | 3.8 |
| studio のバインド | `127.0.0.1` | コンテナ内 `0.0.0.0`、ホストへは `127.0.0.1` で公開 | 7.1 |
| tailnet 上の URL | `https://<現ホスト名>.<tailnet>.ts.net:<port>` | **変わる** | 10.6 |
| 認証 | N1 | N1（同じ経路: ホストの `tailscale serve`） | 7.2 / 7.5 |
| `Origin` の許可値 | 現ホストの URL | **変わる** | `public_url` から導出 |
| GitHub 認証 | ユーザーのシェルの gh。studio は使わない | 同じ。**コンテナには入れない** | 10.5 |

#### Coolify でのデプロイ方式

[確認済] Coolify の方式は Nixpacks / Railpack / Static / Dockerfile / Docker Compose / Docker Image。

| 案 | メリット | デメリット | 評価 |
|---|---|---|---|
| **B1. Docker Compose** | ポート・ボリューム・上限・ヘルスチェック・実行ユーザーが**すべてリポジトリのファイルに残る**（Coolify は compose を正として扱う [確認済]）。Coolify 抜きの `docker compose up` でも動く | Coolify の「Healthcheck」画面は使えない（compose に書く）。「Resource Limits」画面が効くかは [未確認] | **◎** |
| B2. Dockerfile | 画面で完結 | 設定が Coolify の DB 側に残り、再現手順が「画面の操作」になる | ○ |
| B3. Nixpacks | Dockerfile を書かない | 版固定・フォント照合・git 同梱を自動検出の上に載せるのは遠回り | ✗ |

**推奨: B1。**
- ビルドは自宅サーバー上で行う（レジストリを使わない）
- デプロイは Coolify の画面のボタン。自動デプロイ（Webhook）は使わない
- ポートを公開しているため無停止更新にはならない [確認済]。再デプロイ中は数十秒止まる [推測]。未保存の編集は自動保存（2 秒）で守る

| 時期 | やること |
|---|---|
| Phase 1（N100） | プロセス制限ドライバ、`TYPST_STUDIO_DIST` の分離、コンテナ実行時のバインド規則、ヘッダ無しアクセスの絞り込み、`/healthz`、`public_url` からの Origin 導出 |
| Phase M | Dockerfile、compose、ビルド確認、Coolify の設定、移設時検証、切替（8 章） |
| やらない | N100 上でのコンテナ化、マルチアーキのイメージ、レジストリへの公開、Nix 化 |

### 10.9 Claude Code との同居（ホスト側で動かす場合）

目的: 6 章の前提（Claude Code が同じディレクトリを直接編集し、git / gh を実行し、MCP で組版を確かめる）を、コンテナ化しても崩さない。

| 項目 | 方式 | 理由 |
|---|---|---|
| データの置き場 | ホストの作業ユーザーのホーム配下の専用ディレクトリを bind mount | ホストから普通のディレクトリとして git・編集できる |
| コンテナ内のパス | **ホストと同じ絶対パス**でマウントし、`TYPST_STUDIO_HOME` もその値にする | MCP が返すパスや診断の file:line を、ホストの Claude Code からそのまま開ける |
| UID / GID | コンテナの実行ユーザー = ホストの作業ユーザー | Docker は所有者を変換しない [確認済]。ずれると保存で `Permission denied`、git は所有者不一致で `status` を拒否する |
| 不一致の検出 | 起動時に `$TYPST_STUDIO_HOME` の所有者と自分の UID を比べ、違えば説明付きエラーで止まる | `safe.directory` を自動で足して黙って通すことはしない |
| git の読み取り | `git --no-optional-locks status ...` | ホスト側の git 操作とインデックスのロックを取り合わない |
| ファイル監視 | bind mount 上をそのまま監視 | 同じカーネルなので変更通知は届く見込み [推測]。M-V5 で確かめる |
| MCP | ホストで `claude mcp add --transport http typst-studio http://127.0.0.1:8796/mcp` | 現ホストと同じ URL |
| clone・ブランチ・コミット・push | ホスト側で実行（`add-project.sh` もホストで） | 10.5 |
| Coolify のダッシュボード操作 | Claude Code にはさせない | デプロイはユーザーがボタンで行う |

受け入れ条件
- ホストで `git switch` → 5 秒以内に UI のブランチ名が変わる
- ホストの Claude Code がファイルを書き換える → 5 秒以内に UI に反映
- UI から保存したファイルの所有者が、ホストの作業ユーザーになっている
- MCP の `list_projects` が返すパスを、ホストでそのまま `ls` できる
- ホストで `git commit` 中に studio が `git status` を走らせても、`index.lock` の衝突でコミットが失敗しない
